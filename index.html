AI DEV SHARE / FRONTEND SLIDES 我的实战版

我怎么把 AI 编程工具一点点接进研发工作流

这不是工具说明书，也不是模型横评。更像一次阶段性复盘：我最近怎么用 Codex、Claude Code、Skills、MCP、qclaw、WorkBuddy 去做事、踩坑、协作和收口。

Codex 更像执行位

我更关心的不是谁最聪明，而是谁更适合放在工作流的哪个位置。

Claude Code 更像拆解位

这套分享会讲真实成本、桥接体验、协作分工和我目前的判断。

Skills + MCP 补能力缺口

不是先装满生态，而是先知道什么问题该交给什么能力去补。

qclaw + WorkBuddy 往真实任务里接

有些地方我已经很确定，有些地方我还在试，但都值得拿出来讲真话。

01 / Cover Arrow keys / Space / Swipe
PAGE 02 48 小时事件线

我不是先有成熟方法，而是先在混乱里把东西跑起来

这页我想先把背景说清楚：这套分享不是事后总结出来的漂亮框架，而是我最近 48 小时边折腾边形成的真实经验。

1
昨天开始正式折腾 Codex 和 Claude Code 桥接，多 agent 互相讨论和 battle。
2
开始尝试 qclaw / OpenClaw / WorkBuddy 的联通，希望它们能交接任务、互相评审。
3
把话题从“工具能不能聊”切到“能不能看 bug 文档、分析 bug、改 bug”。
4
过程中出现了 token 成本、权限、桥接稳定性、上下文膨胀这些很真实的问题。
5
最后我意识到，应该把这些经验沉淀成一套能拿去分享、还能继续迭代的网页 PPT。
我这页的判断
  • 这些内容的可信度，不来自定义，而来自它们刚刚真的发生过。
  • 我自己也不是一开始就清楚，只是先有动作，再慢慢收成方法。
  • 所以后面每一页，我都尽量讲“我怎么做”和“我现在怎么想”。
02 / Timeline 从折腾到项目化沉淀
PAGE 03 工作流总图

我现在最笃定的一点：工具名不重要，交接链路更重要

如果只记工具名，最后很容易变成一页生态地图。但我最近最有启发的，其实是慢慢看清楚谁该先上、谁该补位、谁该做最后验收。

人定目标
→
Claude Code 拆解 / 复核
→
Codex 执行 / 验证
→
Skills / MCP / Bridge 补能力
→
人验收 / 继续追问
→
沉淀成 SOP / 提示词 / 页面
我现在的分工理解
  • Codex：更像进工程现场干活的人，读目录、改代码、验证结果。
  • Claude Code：更像拆解、互评、补视角的人，适合帮我把混乱问题讲清楚。
  • qclaw / WorkBuddy：不是主角，而是工作任务的交接通道和集成场。
这条链路为什么重要
  • 工具多不是问题，问题是它们如果并列摆着，就很难形成产出。
  • 我真正想讲的是：谁先拆，谁先干，谁来复核，谁来背交付。
  • 这也是后面讲 Skills、MCP 和 Bridge 时，我最看重的判断标准。
03 / Workflow 工具要挂在流程上
PAGE 04 Codex

Codex：让它先试，你再审

我现在最认可 Codex 的位置，不是"比谁更会解释"，而是它更像能进项目现场帮我做事的执行位。

  • 先让它摸目录、看文档、归纳当前上下文，再进入具体任务。
  • 适合做"给我改、给我验、给我落文件"的动作，不只是聊天。
  • 当任务边界清楚时，它的推进速度比我自己手动切来切去快很多。
# 我现在更常见的用法
1. 先让它总结代码库和限制
2. 再让它只改一小块
3. 最后看 diff / 结果 / 风险

我踩过的坑

  • 上下文不够时，它会认真地往错方向干。
  • 如果我自己没定义验收标准，最后很容易"看起来改了，其实没收口"。
  • 把大而糊的任务直接丢进去，效率会明显下降。
04 / Codex 执行前先收边界
PAGE 05 Claude Code

Claude Code：对我来说最强的不是写代码，而是把乱问题拆开

如果要我用一句话形容它现在在我工作流里的位置，我会说：它更像一个很会帮我拆题、对照、互评的搭子，但成本感要一直带着。

我现在最常拿它干什么
  • 先帮我拆解混乱问题，再决定值不值得交给另一个 agent 去做。
  • 做方案比较、互评、battle、复盘，这类“需要补视角”的事它很适合。
  • 面对我这种脑子里有很多碎片、但还没收成结构的时候，它特别有用。
我踩过的坑也很明确
$404.42 长对话一旦失控，token 和费用会先把问题暴露出来。
$83.87 不是只有最强模型贵，第二梯队长期跑下来也会有体感。
225.2M 我现在会主动问自己：这个任务到底值不值得长上下文。

下一页我直接放真实截图，因为这件事靠口头讲不够有冲击力。

06 / Cost 真实数据页
PAGE 07 qclaw / WorkBuddy

这部分我不想吹大，我更想讲一件“已经跑通”的事

qclaw / OpenClaw 和 WorkBuddy 我还没有大规模带进长期真实项目，但我至少已经验证了一条可用的桥接路径：共享目录 + 定时轮询。这一页我只讲我已经确认过的东西。

我已经验证到哪一步了
  • WorkBuddy 和 qclaw 的双向交接，至少在文件级别已经跑通。
  • 当前采用的方案是 共享目录 + 定时轮询，不是最优雅，但足够稳、足够低依赖。
  • 这对我最大的启发不是“桥好酷”，而是跨 agent 协作必须先有一条最朴素的落地通道。
  • 我下一步才会把它往 bug 分析、任务派发、结果回传这些真实工作里带。

这一类结果对我最重要的价值，不是炫技，而是证明：在没有暴露本地 API 的前提下，也能先把交接链路跑起来。

07 / Bridge 先验证一条稳通路，再谈规模化使用
PAGE 08 双 agent 复盘

这次做 PPT，双 agent 没有自动让我更稳

这个结论我想明确讲出来：如果多一个 agent 只是多一层意见、多一轮建议、多一个分叉，那它不但不会更稳，反而会增加返工。这次做 PPT 的过程，我就明显感受到了这件事。

battle 本身并不等于高质量。真正有价值的是：它有没有明确承担批判、对照、校验的职责。

我这次踩到的 4 个问题
  • brief 太宽，讨论可以发散，但执行需要收口，这两者没有被分开。
  • 第二个 agent 很多时候只是在提建议，没有扮演明确的验收或批判角色。
  • 做 PPT / 做前端这种任务，审美和内容判断如果不统一，就会不断返工。
  • 没有统一验收标准时，双 agent 只是把“可能错的地方”翻倍了。
