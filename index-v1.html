怎么把 AI 编程工具接进研发工作流

3 个决策 + 1 套判断框架 + 真实踩坑记录

这不是工具说明书，也不是模型横评。更像一次阶段性复盘：我最近怎么用 Codex、Claude Code、Skills、MCP、qclaw、WorkBuddy 去做事、踩坑、协作和收口。

Codex 更像执行位

我更关心的不是谁最聪明，而是谁更适合放在工作流的哪个位置。

Claude Code 更像拆解位

这套分享会讲真实成本、桥接体验、协作分工和我目前的判断。

Skills + MCP 补能力缺口

不是先装满生态，而是先知道什么问题该交给什么能力去补。

qclaw + WorkBuddy 往真实任务里接

有些地方我已经很确定，有些地方我还在试，但都值得拿出来讲真话。

02 / Roadmap 5 个章节，30 分钟
PAGE 03 关键决策 1/3

转折 ①：不做生态图，做交接链路

问题

最初想把每个工具的能力边界讲清楚，发现越讲越像工具说明书——观众听完不知道"我该用谁"。

做法

把焦点从"工具能做什么"切到"任务怎么在不同工具之间走完"。

原因：观众真正需要的是"我遇到 X 任务该用谁"，不是"谁最厉害"

💡 判断

以后判断内容值不值得写，先问"观众拿走能用吗"，不是"讲的是不是对的"。

→ 结果：分享从"工具罗列"变成了"工作流总图"，每一页都有明确的交接点。

03 / Decision 1 链路比工具名重要
PAGE 04 关键决策 2/3

转折 ②：双 agent 不是双倍效率，是双倍复杂度

问题

想让 Claude Code 和 Codex 同时跑，结果返工率反而更高——两个 agent 都需要完整上下文才能干活，上下文不够时就会往不同方向跑。

做法

强制分工：拆解归拆解，执行归执行，不能同时在一个任务上。

原因：没有角色和验收标准，双 agent 等于把错误翻倍

💡 判断

多 agent 只在"角色明确 + 验收清楚"时才有效，否则是负担。

→ 结果：后面的双 agent 复盘页，就是在验证这个判断。

04 / Decision 2 多agent需要多验收
PAGE 05 关键决策 3/3

转折 ③：成本页不是炫技，是决策依据

问题

Claude Code $404 的账单出来之后才开始认真想"值不值"——长上下文不是免费的，它会在账单上暴露你方法里的漏洞。

做法

把 token 成本和任务价值挂钩：什么任务值得长对话，什么任务应该快拆快干。

原因：建立"拆解任务"和"执行任务"的长度判断标准

💡 判断

以后每个长对话开始前，先问"这个任务值多少 token"。

踩过的坑
  • 双 agent 做审美决策 → 无标准 → 返工 4 次审美无法对齐
  • qclaw ↔ WorkBuddy 用 API → macOS 沙箱隔离方案被封死
  • 上下文不够让 Codex 执行 → 认真地往错方向干先拆再给

06 / Workflow 一个真实案例走完链路
PAGE 07 Codex

Codex：让它先试，你再审

我现在最认可 Codex 的位置，不是"比谁更会解释"，而是它更像能进项目现场帮我做事的执行位。

  • 先让它摸目录、看文档、归纳当前上下文，再进入具体任务。
  • 适合做"给我改、给我验、给我落文件"的动作，不只是聊天。
  • 当任务边界清楚时，它的推进速度比我自己手动切来切去快很多。

Codex 执行现场：工具调用 43 次、过程消息 23 条，全部完成。执行位的优势是"干完能收口"，不只是聊完没下文。

踩过的坑
  • 上下文不够时，它会认真地往错方向干误执行
  • 没定义验收标准 → "看起来改了，其实没收口"假完成
  • 大而糊的任务直接丢进去，效率明显下降先拆再给
07 / Codex 执行前先收边界
PAGE 08 Claude Code 决策卡

拆解强，但不是在所有任务上

这张卡总结我现在的判断标准：什么时候用它、什么时候不用、什么时候要踩刹车。

✅ 适合用 Claude Code 的场景
  • 问题边界不清楚，需要有人帮你拆解和收口
  • 需要补视角、做方案比较、battle 方向
  • 脑子里有很多碎片，需要有人帮你结构化
  • 需要互评：你有一个方向，让它帮你找漏洞
  • 任务价值高，值得投入长上下文

→ 判断标准：任务的价值 > 上下文的成本？

❌ 不适合用 Claude Code 的场景
  • 任务边界已经很清楚，不需要再拆解
  • 重复性执行动作（改代码、跑脚本）→ 用 Codex 更便宜
  • 审美判断（PPT 风格、UI 方向）→ 无客观标准，agent 对齐成本高
  • 需要实时交互的调试 → 长上下文会堆积无效信息

→ 判断标准：这件事 Claude Code 做比人做更划算吗？

08 / Claude Code 适合/不适合 + 成本决策框架
PAGE 09 判断清单

如果只记住一句话

每一页讲了很多，但这页我想提炼出每页最核心的那个判断。以后你遇到类似情况，可以直接用。

关于工具选择
  • 先问"观众拿走能用吗"，不是"讲的是不是对的"
  • 谁先拆、谁先干、谁来验收——链路比工具名重要
  • 多 agent 只在"角色明确 + 验收清楚"时才有效
关于 Claude Code
  • 任务价值 > 上下文成本时用它，否则用 Codex
  • 先想"这个任务值多少 token"，再开始长对话
  • 审美判断、实时调试不适合用长上下文 agent
关于 Codex
  • 任务边界清楚时才给它，否则会往错方向干
  • 适合：改代码、跑脚本、验证结果、重复性执行
  • 不适合：拆解混乱问题、方案比较、审美决策
关于双 agent 协作
  • 没有统一验收标准时，双 agent 把错误翻倍
  • 审美判断无法对齐：PPT 返工 4 次才收口
  • 上下文不够时两个 agent 会往不同方向跑

🔑 核心判断：AI 工具的价值不在于"有多强"，而在于"放在链路哪个位置最合适"。

PAGE 11 双 agent 复盘

这次做 PPT，双 agent 没有自动让我更稳

如果多一个 agent 只是多一层意见、多一轮建议、多一个分叉，那它不但不会更稳，反而会增加返工。

battle 本身并不等于高质量。真正有价值的是：它有没有明确承担批判、对照、校验的职责。

踩过的坑 根因 下次怎么做
Brief 太宽 发散和收口没分开 先写 Brief 再写 SOP
agent 角色模糊 没定义批判职责 给 agent 写清楚 role
审美不统一 主观判断无标准 提供参考样例
无统一验收 双倍错误 先写 acceptance criteria

🔑 核心教训：双 agent 不是神话——没有清晰角色和验收标准，多一个 agent 只是多一个出错的可能。
